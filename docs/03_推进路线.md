# 推进路线：先做什么、怎么拆、3D 怎么落地

> 写于 2026-10-23。补 `01_实现方案.md` 没讲透的三件事：先后顺序、怪化猫的繁复画风怎么搬进 Tripo + Three.js、3D 的穿模和碰撞怎么处理。
> 和 01 不一致的地方以本文为准（主要是镜头：01 写的是"固定机位 + 分层视差"，现在改成能自由走动的 3D，镜头受约束）。

## 一、先做玩法还是先做设定？

两个都不是"先做完一个再做另一个"，而是按**风险**排：哪件事做错了返工最贵，就先验证哪件。

这个项目最贵的三个风险：

1. **画风搬不进 3D**：平涂、彩色描边、满身纹样、和纸，在实时 3D 里看起来像廉价卡通渲染。
2. **角色动起来穿模**：药贩子的长衣服、大袖子、头巾，Tripo 出来是一整块网格，一走路腿就从衣服里戳出来。
3. **Tripo 出的东西风格漂、比例乱**，批量出完才发现用不了。

霍格沃茨那边已经踩过第 3 条的坑：75 个素材先全部出完，进了 Unity 才发现礼堂比概念图差很多。所以这次的顺序是：

| 顺序 | 做什么 | 为什么在这个位置 |
|---|---|---|
| 1 | **玩法骨架一页纸**：视角、移动方式、有没有战斗、一局多长、核心循环 | 视角决定素材要做到什么精度、背面要不要做、穿模能藏多少。不先定，后面全是猜 |
| 2 | **灰盒画风样片**：不用 Tripo，Blender 里拉几个方块拼一段走廊，Three.js 里跑卡通着色 + 描边 + 纹样 + 和纸 | 验证风险 1。一天能出结果，一个积分不花 |
| 3 | **一个角色走通全链路**：药贩子 概念图 → Tripo → Blender 整理绑骨 → Three.js 里在灰盒走廊里走一圈 | 验证风险 2 和 3。只做一个，出问题改流程，不浪费 |
| 4 | **垂直切片**：一段完整走廊 + 药贩子 + 一个 NPC + 一条线索 + 一段对话 | 第一次能"玩"，所有系统都有了最小版本 |
| 5 | 补完 形・真・理 全流程 | 玩法完整 |
| 6 | 批量出其余素材、扩场景 | 流程已经验证过，这时候批量才安全 |
| 7 | 过场、音效、标题卡、上线 | 收尾 |

**人物设定、场景设计放在哪？** 另一个对话正在做的画风确认（色板、主参考图、场景概念图）就是第 2 步和第 3 步的输入，和第 1 步可以同时进行。但**详细的人物设定（性格、台词、物怪背景故事）往后放到第 4 到 5 步**，那是内容，不是风险。

## 二、玩法骨架（第 1 步要拍板的几件事）

建议的默认值，你改哪条告诉我：

| 决定 | 建议 | 理由 |
|---|---|---|
| 视角 | 第三人称，镜头**分区固定 + 跟随**：走廊里镜头沿轨道跟着人平移，进房间切到预设机位 | 像原作的构图（正侧面、斜俯视），而且镜头永远不会钻进墙里，穿模也好藏 |
| 移动 | WASD / 点击移动，**只走不跑不跳** | 药贩子本来就是慢慢走；不跳就不用做高度碰撞，关卡全是平地 |
| 战斗 | **没有实时战斗**。高潮是"拔剑"过场 | 战斗要打击感、受击动画、敌人 AI，工作量翻三倍，而且最容易穿模 |
| 交互 | 靠近线索按 E，天秤摇得越厉害离线索越近 | 原作元素，又是天然的寻路引导 |
| 长度 | 一局 15 到 20 分钟，一个物怪一个案子 | 能做完 |

一句话核心循环：**走 → 天秤响 → 找到线索或问人 → 拼出 形/真/理 中的一个 → 继续走**。三个都齐了拔剑。

## 三、繁复画风怎么搬进 3D

核心思路：**Tripo 只管"形状"，所有"花纹和颜色"都交给我们自己的着色器。** 怪化猫的繁复几乎全在表面（纹样、金箔、色块），形状本身其实很简单（直线建筑、筒状衣服）。Tripo 恰好形状还行、表面会烘糊，所以这样分工正好。

### 1. 纹样：用"屏幕空间贴图"，这是原作本来的做法

原作有个很有名的特点：**衣服上的花纹不跟着褶皱走，而是像贴在屏幕上一样**，人物动的时候花纹是"透出来"的。这对我们是好事：

- 不需要 Tripo 出好 UV（Tripo 的 UV 是碎的，没法正常贴平铺纹样）
- 着色器里按屏幕坐标（或物体空间的三平面投影）采样纹样图，直接得到原作的效果

具体做法：

1. Tripo 出的模型在 Blender 里**按区域刷顶点色当"材质分区"**：比如红 = 外衣、绿 = 内衬、蓝 = 腰带、黑 = 头发、白 = 皮肤。这一步可以半自动（按 Tripo 贴图的颜色聚类），再手修。
2. Three.js 着色器读顶点色，每个分区查一张表：底色是什么、叠哪张纹样、纹样缩放多少。
3. 纹样库（市松、麻叶、青海波、七宝、云纹）自己画或程序生成，统一在 `public/textures/patterns/`。

这样改配色、换纹样只改一张表，不用重新跑 Tripo。

### 2. 描边：两种方法分开用

| 对象 | 方法 | 原因 |
|---|---|---|
| 角色、道具 | 背面外扩（inverted hull），描边颜色按分区给 | 稳定，粗细可控，不闪 |
| 建筑、背景 | 后期按深度和法线找边 | 建筑都是直线，后期描边干净；而且省去每个模块做外壳 |

### 3. 建筑不要用 Tripo

Tripo 出的建筑直线是歪的、重复构件对不齐，拼走廊会接缝。大奥的建筑全是横平竖直的木构，用 **Blender 脚本程序化生成模块**（柱子、梁、拉门、畳、廊板），我写 Python，参数化尺寸。这些模块面数低、UV 规整、碰撞体可以直接从同一个脚本导出。

Tripo 用在它擅长的地方：**角色、物怪、造型不规则的道具**（唐伞、行灯、药箱、天秤、剑）。

### 4. 远景和装饰用画片

拉门上的画、天花板的格子画、庭院远景、天空，**不建模，做成平面贴图**（图片模型出图，统一风格）。原作本来就是纸戏一样一层层叠的，平面在这里不是偷工，是风格。注意平面贴到墙上要稍微抬起一点或开 `polygonOffset`，避免和墙面闪烁打架。

### 5. 和纸和色调：后期统一

和纸纹理、轻微暗角、色板压缩（把颜色量化到靠近主色板）放在最后一层后期。不管 Tripo 出来的颜色偏多少，过一遍后期都会被拉回同一套色调，这是保证一致性最省事的一道保险。

## 四、穿模和碰撞

### 角色自己穿模（衣服、袖子、头发）

这是 Tripo 角色最大的问题：出来是一整块网格，自动绑骨只认人体，长衣服会被腿骨拉着变形。

**原则：设计不为技术让步。** 大袖、长下摆、层叠的和服、飘带、头巾都保留，主参考图照原片的精致度画。代价是主要角色不能只靠 Tripo 自动绑骨，要多花几天在 Blender 里做"衣服层"。这正是商业动画风游戏（原神、绝区零一类）处理长衣服的做法：

1. **身体和衣服分开**：Tripo 出的整块模型在 Blender 里拆成"身体"和"衣服"（外衣、内衬、袖子、下摆、头巾、腰带各一块）。Tripo 有部件拆分功能，拆不干净的手拆。也可以让 Tripo 单独再出一个"只有身体"的版本当底。
2. **被衣服完全盖住的身体直接删掉**：长袍里面的腿、袖子里面的胳膊，只留骨骼不留网格。看不见的东西不存在，就不可能戳出来。这是游戏里最常用、最有效的一招。
3. **衣服挂物理骨链**：下摆、大袖、头巾、飘带各挂一串骨头，运行时用弹簧骨（three-vrm 的 SpringBone 或自写）让它们跟着动作甩起来。腿和手臂上放几个碰撞球，骨链碰到就被推开，下摆不会被腿穿过去。
4. **固定动作直接烘焙布料**：待机、走、转身、拔剑这些动作数量有限，可以在 Blender 里对衣服做真正的布料模拟，再把结果烘焙到骨链上导出。效果和离线动画一样，运行时零成本。弹簧骨只负责动作之间的过渡和停下来时的余摆。
5. **修正形态键**：抬手、弯腰这类大动作，在关节处做几个修正形态键，防止衣服在肩膀、腋下塌陷。

**实际做法（2026-10-27，药贩子 v2）**：上面 1、2、3 已落地，4、5 还没做。
- Tripo 的网格被 UV 接缝切成两百多块，没有"身体在衣服里面"这回事（是一层壳），所以第 2 条不用做；第 1 条也不靠部件拆分，而是 `tools/blender_layers.py` 按"位置 + 贴图颜色"的连续规则分出下摆、左右大袖、长发四层，再按面拆成五个独立网格。权重只由位置决定，拆开的接缝不会裂。
- 骨链：下摆 12 条 × 3 节挂骨盆，贴着外层衣服量出来；大袖每边 2 条 × 2 节挂前臂；长发 5 条 × 3 节挂头。原来绑在腿上的权重转给骨盆（袖子区域转给前臂），只有凉鞋、足袋、袴的裤脚还跟腿走。
- 运行时 `web/src/spring.js`（自写，做法同 VRM SpringBone）：惯性 + 回弹 + 重力，腿和躯干是胶囊碰撞体，碰撞半径在绑定姿势下逐节校准。参数在 `web/src/data/spring.json`。
- 结果：横斩时下摆不再被两腿扯成一张膜，是垂着的锥形，前腿会把前襟顶出去一点；大袖在抬手时会垂下来。对比图 `assets/processed/shots/layer_对比_分层骨链.jpg`。

**精致度主要在表面，表面这块不打折。** 原作的精致大半在纹样、金线、脸上的妆。纹样走着色器（第三节），分辨率不受 Tripo 影响；脸上的妆和眼睛用单独的高清手绘贴图投到脸上，眨眼和表情换贴图，像原作一样是"画出来的脸"。药贩子作为主角，面数给到 3 到 5 万，对话时的近景镜头能扛得住。

工作量分级：

| 角色 | 做法 | 大概工时 |
|---|---|---|
| 药贩子 | 上面 1 到 5 全做 | 3 到 5 天（大部分是脚本，你只看效果） |
| 阿浅、阿龟等有戏份的 NPC | 1、2、3 做，不烘布料 | 每个 1 到 2 天 |
| 背景女中 | 站桩，不绑骨或只做待机 | 半天 |

动作上仍然建议慢走为主，这是原作药贩子的气质，不是为了躲穿模。

### 角色和场景穿模

- **碰撞不用模型本身**：角色用胶囊体，场景用 Blender 脚本导出的简单盒子（墙、柱、家具各一个盒），物理用 Rapier（`@dimforge/rapier3d-compat`，有现成的角色控制器）。Tripo 模型的网格又碎又重，拿来做碰撞会卡、会抖。
- **地面全平**：不跳、不上楼梯（要换楼层就用过场黑屏切），省掉一大类问题。
- **拉门开关**：门是触发器，开门时把门的碰撞盒关掉，不做物理推门。
- **NPC 站桩**：NPC 不走动，或者沿固定路线走，碰撞只是一个圆柱。
- **剑和道具挂点**：在骨骼上加空节点（手、腰），道具挂上去；拔剑过场直接用 Blender 渲的视频，不在实时里做手握剑的动画，躲掉最容易穿帮的一段。

### 镜头穿墙

分区固定 + 轨道跟随的镜头本身就不会穿墙，这是选这种镜头的另一个原因。如果某个房间要自由转镜头，加一条从角色到镜头的射线检测，撞墙就把镜头拉近。

### 比例和朝向

Tripo 每次出的模型大小、朝向、原点都不一样。Blender 整理脚本统一做三件事：按清单里写的真实高度缩放、原点放脚底、正面朝 -Z（Three.js 的约定）。清单里每个素材都写高度，霍格沃茨的 `assets.json` 已经是这么做的。

## 五、UE 什么时候上

结论：**这一版不用 UE。**

- 这个画风的难点全在自定义着色和后期，Three.js 写 shader 比 UE 改材质图更直接，而且我能直接改、你刷新就能看。
- 网页链接一点就玩，适合配合你的视频发布。UE 做网页要租串流服务器。
- 你要的东西（小场景、少量角色、无战斗）不碰 Three.js 的性能上限。

会改主意的情况：以后想做大地图、复杂战斗、或者想上 Steam 出桌面版。到那时着色器思路可以照搬到 UE 的材质里，Tripo 和 Blender 那段流程不用变。

## 八、Spark 泼溅的坑（2026-10-23，接第二块泼溅时踩的）

| 现象 | 原因 | 对策 |
|---|---|---|
| 镜头一偏整块泼溅消失，画面只剩背景色 | Spark 算的包围盒不对，被 three 的视锥剔除 | `splat.frustumCulled = false` |
| 镜头贴墙半米内画面糊成一片 | 墙上的高斯球放大盖满屏幕 | 机位离泼溅的墙至少 1 米，走廊轨道镜头 range 收进来 |
| 运行时改泼溅的 `visible` / `opacity` / `position`，或挂 `SplatEdit` SDF 裁剪 | Spark 重建合并缓冲时把可见点数算成 0，渲染目标尺寸为零，WebGL 报错刷屏，之后整个泼溅系统不画 | 泼溅的集合和变换只在加载时定；要裁掉房间泼溅门外脑补的走廊，用 `tools/spz_clip.py` 在文件层面删点 |
| 浏览器面板藏在后台时，泼溅时有时无，活跃点数 0 | 页面在后台定时器被限到 1 秒甚至 1 分钟一次，Spark 回读 GPU 深度靠定时器轮询，一次排序要几秒到几分钟 | 不是故障。页面可见时排序只要几毫秒。不要加"排序卡住就复位"的看门狗，复位会打断回读，结果永远是 0 |
| 两块泼溅都在场时，同步渲染只在全景图原点附近能看到房间 | 同上（后台限速），排序没完成 | 实机验证要在可见窗口里做 |

房间泼溅的坐标约定：全景图相机点 = 房间中心，原始帧 y 向下、正前方 +z；先绕 X 转 180°，再绕 Y 转 yawDeg 把正前方对准房间里墙，缩放用 `metric_scale_factor`，地面 `ground_plane_offset × scale` 抬到 0。碰撞网格里门外那 6 米是 Marble 顺着全景图里的走廊脑补的，裁掉。

**房间泼溅的实际形状（2026-10-27，三间房都一样）**：World Labs 生成的房间比提示词里写的小（女中房 3.6×5.0 米，阿雪空房 2.6×3.5 米），全景相机贴着门那面墙（门墙在原始 z≈-0.75），门墙外是顺着全景图里的拉门脑补出来的一截走廊。摆放时门墙离走廊墙留 1 米当入口过道，过道外用 `spz_clip.py` 裁掉；用 `tools/room_place.py` 算。全景相机附近画质最好，房间机位放在里墙前朝门看（里墙在镜头背后，贴得近也不糊）。

**内置浏览器画不出泼溅**：会话没在任何窗口里显示时，内置浏览器的页面在屏幕外跑，Spark 的 GPU 回读排序回不来，泼溅整块空白，连单独的泼溅查看器也一样。这时只能验证布局和逻辑，画面要在可见窗口里看。

**地面高度别信 `ground_plane_offset`（2026-10-27）**：World Labs 的 world.json 给的地面值，阿雪空房准（1.006 对实测 1.0），女中房偏 0.17（换算 21 厘米），歌山房偏 0.35（52 厘米）。实测方法：读 `splat_500k.spz`，取房间内（z>-0.5、|x|<1.2、不透明度过半）点的 y 直方图，y 向下，最大 y 处最密的那一层就是榻榻米面。`room_place.py --floor` 传这个值。

**内置浏览器在后台会暂停逐帧循环**：页面不在屏幕上时 requestAnimationFrame 不跑，Spark 靠逐帧循环驱动，所以泼溅空白；手动调渲染也不行。验证画面要在可见窗口里做，游戏台的 `?at=房间名` 可以直接跳进房间。

**更正（2026-10-28）**：内置浏览器画不出泼溅，真正的原因是浏览器面板没显示时页面宽高是 0。用浏览器工具的模拟视口（比如 1280×760）给它一个尺寸，再手动驱动几帧渲染，泼溅就能正常截图。之前以为是后台限速，不对。

**碰撞网格怎么用（2026-10-28 场景线）**：`collider.glb` 和泼溅在同一个原始坐标系，地面完全重合，可以直接当碰撞。`tools/walkmap.py` 预算成 0.1 米栅格，运行时 `web/src/world/collision.js` 查表。三个坑：
1. **走廊泼溅的地面是斜的**：Marble 把长走廊重建成往远处下沉的坡（13°），游戏里尽头比门口低 2 米，角色站在 y=0 就悬空。房间泼溅只有 2° 左右。墙是竖的，所以不是整块转了个角度，不能用旋转修。`tools/spz_level.py` 按碰撞网格的地面剖面离线剪切校平，协方差逐点重算（编解码往返误差中位 0.9%）。以后长空间出完都先拟合一下地面坡度。
2. **有天空的场景（中庭）碰撞网格带一个天空穹顶**，大斜面盖住整个院子。障碍判断要按这一格正上方的插值高度，不能按整个三角形的高度范围。
3. **全景相机不在房间中间**：中庭的全景相机离门墙 2 米、离对面回廊 3 米。摆放前先按 z 切片找门墙（墙宽突变的地方），再用 `room_place.py`。World Labs 的米制系数会让院子和隔壁房间重叠，要先算重叠再定缩放。
